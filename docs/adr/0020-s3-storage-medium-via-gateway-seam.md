# S3 is a byte-stream storage medium reached through a gateway seam, modeled on the HTTP medium and the Sheets seam

Flowthru reads and writes S3 through `Flowthru.Extensions.AWS.S3` — an `IStorageMediumProvider` claiming the `s3://` scheme, so any format (Csv / Parquet / Json / Xml / …) works over S3 unmodified through the existing **Medium → Format → Container** composition. This is the deliberate counterpart to the Sheets decision ([ADR-0027](./0027-google-sheets-catalog-extension.md)): a Google Sheet is a *typed tabular store* and is an `IStorageAdapter` in the EFCore grain; an S3 object is a *bytestream* and is an `IStorageMedium` in the file/HTTP grain. The same data — picking the right Core extension surface for the backend's actual shape — produces opposite structures, and that is correct. Adding S3 is purely additive: one provider plus a DI registration, **no Core change**, mirroring the `IStorageMediumProvider` contract the HTTP medium already established.

**The medium calls a narrow `IS3Gateway` seam, not the AWS SDK.** Exactly as `ISheetsGateway` confines `Google.Apis.Sheets.v4` to one class, `IS3Gateway` confines `AWSSDK.S3` to one class (`AmazonS3Gateway`). The seam speaks a Flowthru-neutral `(bucket, key)` + `Stream` vocabulary — `GetObject` / `PutObject` / `ObjectExists` / `DeleteObject` / `GetETag` — so the shipped offline stub (`LocalFileS3Gateway`) satisfies it with **zero** AWS dependency, and tests run fully offline. The swap is at gateway registration: `UseS3()` wires the AWS-backed gateway, `UseLocalS3(root)` wires the file-backed stub, `UseS3(IS3Gateway)` wires any gateway; the provider, the medium, and every catalog item are identical across all three. This is the user-requested "same approach as Google Sheets, including a local file-based stub for testing."

**Offline support is a shipped file-backed stub, not a separate package.** `LocalFileS3Gateway` maps each object to `{root}/{bucket}/{key}` and is a legitimate shipped local-dev backend (the same call the user reaches for when developing without an AWS account), following the `JsonFileSheetsGateway` precedent. Unlike Sheets, an object store is already bytestream-shaped, so there is **no `LocalS3Store` / JSON model layer** — the filesystem *is* the store. Keys are confined under the root (a `..`-escaping key is rejected), and writes go through temp-file + atomic rename, mirroring `FileStorageMedium`.

**Credentials come from the standard AWS chain; nothing is hardcoded.** The production gateway builds its `IAmazonS3` with no explicit credentials, so the SDK resolves them itself (environment, shared profile, ECS/EC2 role). `S3Options` carries only endpoint/addressing — `Region`, `ServiceUrl`, `ForcePathStyle`, `Timeout` — and `ServiceUrl` + `ForcePathStyle` make the same extension target any S3-compatible store (MinIO, LocalStack, R2). A secret never enters the catalog or the DAG.

**Writes are atomic, so `IsTransactional = true` is honest.** A single S3 `PutObject` replaces the object all-or-nothing — there is no partial-object visibility — so a failed write leaves no torn state. This follows the same atomic-write reasoning the Sheets adapter uses (one atomic `batchUpdate` → `IsTransactional = true`). `CanStream = true` (reads stream the response body); `CanAppend = false` (S3 has no in-place append); `IsPersistent = true`. Large objects beyond a single PUT (multipart upload) are out of v1; the common path — a format serializer handing a seekable `MemoryStream` — is one PUT.

**Pre-flight write-reachability is a sentinel PUT+DELETE.** `InspectTarget()` PUTs a zero-byte sentinel beside the target key and best-effort deletes it, mapping any refusal — denied `s3:PutObject`, missing bucket, unreachable endpoint — to a `WriteAccessDenied` `ValidationResult` at pre-flight rather than a runtime exception. This is the direct mirror of `LocalFileWriteProbe`'s filesystem sentinel and the only honest way an object store proves write access ahead of execution. It briefly creates an object (which can fire bucket notifications) — the same trade-off the filesystem probe already makes.

**S3-backed items are cacheable via ETag.** The medium implements `ISupportsFingerprint` over the object ETag (one HEAD, no body transfer) — stable, content-sensitive, cheap — exactly the HTTP medium's approach. An absent object surfaces a FlowIO failure ("fingerprint unknown" → cache miss), never a pre-flight abort.

## Considered Options

- **A direct `IStorageAdapter` like Sheets/EFCore** — rejected. That grain is for typed tabular *stores* that validate `TRow` against a schema. An S3 object is opaque bytes with no schema; it belongs on the Medium axis, where it composes with every format for free. Modeling it as an adapter would forfeit format reuse and duplicate what the resolver already does.
- **Calling `AmazonS3Client` directly from the medium** — rejected. It would force the offline stub and every test to reference `AWSSDK.S3`, and couple the medium to a concrete, awkward-to-fake SDK client. The neutral seam confines AWS to one class and makes the local stub a first-class backend.
- **A container-based integration test (LocalStack / MinIO via Testcontainers)** — rejected as the *default* tier. It forces Docker into the default test flow for a bytestream backend the file-backed stub already emulates faithfully. Instead, `S3GatewayLaws` runs the same behavior suite over the always-on local stub and a capability-gated (`FLOWTHRU_S3_TEST_BUCKET`) live AWS tier — the offline tier is what makes the stub a *verified* S3 stand-in; the live tier is the "or a real bucket" path, Inconclusive when unconfigured.
- **`HeadBucket`-only write probe** — rejected. It is cheaper but only proves reachability, not write permission; the sentinel PUT is the honest write-reachability probe and matches the filesystem medium.
- **`IsTransactional = false` (conservative, mirroring `FileStorageMedium`)** — rejected. A single-object PUT is genuinely atomic; declaring `false` would understate the medium's real capability, and the Sheets ADR already set the precedent of declaring the flag from actual atomicity rather than defaulting it.

## Consequences

- **No new Core diagnostics.** The provider emits no Roslyn/source-gen diagnostics; pre-flight `WriteAccessDenied` flows through Core's existing `FT3xxx` aggregation. `FTS3` is reserved for any future S3 analyzer but none is allocated now.
- **The worked example is deferred to the deployable-Lambda example (#73)**, which is explicitly that example and blocked by this work. #69's round-trip is proven by `S3BackedJsonItemTests` plus the medium / fingerprint / gateway Laws — not a standalone `examples/` project.
- **Multipart upload (objects beyond one PUT) and an S3-backed cache manifest are out of v1.** The cache manifest opt-in belongs with the Lambda harness's no-cache-by-default story (#70).
- **Older S3-compatible servers may reject AWS SDK v4 request checksums.** Documented in the README; AWS itself is unaffected, and the default (file-stub) test flow does not exercise it.
