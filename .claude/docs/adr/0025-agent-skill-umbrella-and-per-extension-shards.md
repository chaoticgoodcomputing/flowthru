# Agent skills: one umbrella skill for breadth, per-extension shards for depth

Flowthru ships its agent guidance as an installable **Agent Skill** (the [agentskills.io](https://agentskills.io) `SKILL.md` format), consumed three ways from one source: in-repo by Claude Code, out-of-repo by any harness via `npx skills add chaoticgoodcomputing/flowthru`, and bundled into every `dotnet new` template. Rather than one monolithic skill or a flat pile of per-topic skills, the guidance is **hybrid**: a single umbrella `flowthru` skill carries the breadth (the schema → catalog → step → flow model, the layered project structure, the end-to-end workflow) and an *actionable index* of what extensions exist; each extension carries its own depth as a [[Skill shard]].

The umbrella lives at `.claude/skills/flowthru/` — `SKILL.md` plus three progressively-disclosed subdocs (`flow-developers.md`, `catalog-developers.md`, and the generated `extensions.md`). A shard lives at `src/extensions/<Ext>/SKILL.md`, beside the extension's README and the shared per-context `CONTRIBUTING.md` — the same co-location the [[Shippable package]] doc standard already uses, extended by one Quality-Bar item. The shard is dual-purpose: its `metadata.flowthru` frontmatter (`extension`, `surface`, `capability`, `register`) is generated into the umbrella's `extensions.md` capability index, and its body *is* a standalone deep skill. So a downstream agent working in a project that uses, say, Python + Parquet + EFCore pulls `flowthru` plus exactly `flowthru-python`, `flowthru-parquet`, `flowthru-efcore` — not eleven extensions it will never touch — and the umbrella's index tells it *which command* to run to pull each one.

Two mechanical seams make this hold together as source-of-truth-driven generation, matching Flowthru's documentation-honesty model (ADR-0008). **The index and the vercel-skills plugin manifest are generated** from the shards (`scripts/generate-skill-extensions.mjs` → `.claude/skills/flowthru/extensions.md` managed block + `.claude-plugin/marketplace.json`), so adding a shard needs no manual index or manifest edit, and a `--check` freshness test (`tests:_test:skill-index-freshness`) fails on drift. **Every code example in a skill is real example source**, spliced through the same `#region docs:` → snippet pipeline the docs use (`scripts/sync-doc-snippets.mjs`, generalized to walk the skill surfaces alongside the docs so the orphan-snippet gate sees one consumer set) — a skill example cannot silently drift from the code it cites. A linking precedent completes it: any reference to a repo project/example/file is an absolute `github.com` URL (clickable for a human, fetchable for an agent), because a skill is read from an *installed copy* where a repo-relative path resolves to nothing; `scripts/_test/skill-links.mjs` enforces it.

## Considered Options

- **Skill granularity** — one monolithic `flowthru` skill (every extension inlined; a downstream agent carries all sixteen regardless of stack), full federation (no umbrella; N independently-installable skills a user assembles by hand), or the hybrid (umbrella for breadth + shards for depth). Chose hybrid: the monolith wastes context on irrelevant extensions and can't go deep; pure federation loses the "what's possible / how do I pull it" discovery surface. The umbrella's generated index *is* that surface — an agent scans it, detects the project's stack from its `.csproj`/`Program.cs`, and pulls the matching deep skills on demand.
- **Shard artifact** — a section inside the extension README, a bespoke non-`SKILL.md` sidecar, or a real `SKILL.md`. Chose a real `SKILL.md` under `src/` (not a default discovery location, so it never pollutes an in-repo session) exposed only through the `marketplace.json` manifest. This makes each shard individually installable *and* keeps the README as human reference/how-to while the shard is agent how-to.
- **Skill code examples** — hand-authored (drifts), or transcribed from real example source via the existing snippet pipeline. Chose real source. The alternative of a parallel `skill:`-namespaced snippet pipeline was rejected: it would fork the extractor and split the orphan-snippet gate; generalizing the one splicer to walk docs + skills together keeps a single honesty gate.
- **Pack injection target** — a tooling-neutral bare `SKILL.md` at the template root (the prior, now-broken behavior) vs. the ready-to-use `.claude/skills/flowthru/` dir. Chose the latter: with four umbrella files a root drop is noise, Claude Code is the primary audience, and `npx skills add --copy` relocates for other harnesses.

## Consequences

- **A shard is Quality-Bar item #5** for every extension (`src/extensions/CONTRIBUTING.md`), alongside XML docs, a README, tests, and a worked example. An extension without a shard is incomplete.
- **A `SKILL.md` under `src/extensions/` bends the "agent infrastructure lives under `.claude/`" rule.** Accepted deliberately: the shard is co-located agent documentation, owned by the extension developer exactly as the README and CONTRIBUTING beside it are.
- **The manifest and index couple to the shard set**, freshness-gated in the `tests` barrel (reliably affected by any `src/extensions/**` change). A shard-only edit that breaks a snippet sentinel without touching examples relies on the CI working-tree diff as the backstop, since `docs` is affected via examples, not `src/extensions`.
- **The fan-out surfaced Quality-Bar gaps**: `Flowthru.Extensions.AWS.S3` has no worked example, and `Flowthru.Extensions.EFCore.Npgsql`'s worked example uses the EF Core *provider* (`UseNpgsql`) but not the *extension's* API (`.NpgsqlTable`/`AddBulkTransfer`). Those two shards fall back to README-verbatim code with an honest source note rather than a real-source snippet, and the gaps are tracked for a follow-up worked example.
- **Skills inherit Flowthru's version code from the monorepo, not a frontmatter field.** vercel-skills content-addresses a skill by its GitHub folder tree SHA (`skills update` compares that hash), so there is no semver to stamp or sync. Because the skills are committed in the same repo that is tagged `vX.Y.Z` per release, `npx skills add chaoticgoodcomputing/flowthru@vX.Y.Z` pins them to the exact published version alongside the packages — version-sync is a property of the tag, not a stamped field. A cosmetic in-skill version marker was considered and rejected: it is inert to the tooling and would churn every shard each release.
- **Per-template deep-skill injection is a deliberate non-goal for now**: the pack injects only the umbrella, and the umbrella teaches the agent to pull stack-matched shards. Injecting `flowthru-efcore` into the `SpaceflightsEFCore` template (etc.) is a future enhancement, not a requirement.

Code this decision governs: `scripts/generate-skill-extensions.mjs`, `scripts/sync-doc-snippets.mjs` (+ `generate-doc-snippets.mjs`, whose snippet artifacts carry a generated `_(source: …)_` provenance line — attribution is never hand-authored), `scripts/_test/skill-links.mjs`, `.claude/skills/flowthru/**`, `src/{extensions,core}/*/SKILL.md` (core packages that are optional add-ons carry shards too — e.g. `Flowthru.FUnit` → `flowthru-funit`, surface `testing`), `.claude-plugin/marketplace.json`, `tests/project.json` (`_test:skill-index-freshness`, `_test:skill-links`), `docs/project.json` (`sync-snippets`, `_test:snippet-freshness`), `nx.json` (`pack`), `examples/starter/project.json` (`_inject_flowthru_skill`), `src/extensions/CONTRIBUTING.md` (§ "The Skill Shard").
