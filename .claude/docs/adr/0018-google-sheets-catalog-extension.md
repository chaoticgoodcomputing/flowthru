# Google Sheets is a typed tabular catalog store, modeled on EFCore

Flowthru reads and writes Google Sheets through `Flowthru.Extensions.Google.Sheets` — a direct `IStorageAdapter<IEnumerable<TRow>>` (the EFCore/GQL grain, not the Medium → Format → Container composition) over the officially-vendored `Google.Apis.Sheets.v4` client. Sheets is modeled as a **typed tabular store in the EFCore mold**: a catalog item is a table of typed rows whose columns correspond to `TRow`'s properties. The write unit is one tab/table, never the spreadsheet — Flowthru owns a "Raw Data" surface and must not clobber the human-readable formula tabs that reference it.

**No cell concept in Core.** Sheets *can* do per-cell typed writes, but Flowthru does not need to model that. An earlier draft promoted a per-cell `ICellSerializable` marker into Core (a "cell-faithful schema" capability) on the premise that Sheets is a serialization *format* needing a typed-scalar marker alongside `ITextSerializable`/`IBinarySerializable`. Native Sheets **Tables** reveal the better model: Sheets carries a *column schema* (`TableColumnProperties` — typed columns + names), which makes it a typed tabular *store* — exactly like EFCore, which carries no serialization marker at all (`EFCoreStorageAdapter<T> where T : class`, validated against the `DbContext` model). Stores validate `TRow` against their own schema; formats need serialization markers. Sheets is a store. So there is no cell concept and no new Core marker: the adapter constrains on `IFlatSchema` (tabular) and validates `TRow`'s columns against the live table schema at pre-flight, mirroring EFCore's `ShapeValidator`.

**The schema-carrying mechanism is native Tables (verified).** A catalog item is addressed by `(spreadsheetId, table name)`; the gateway resolves the table to its range + `ColumnProperties`; Flowthru creates the table from `TRow` if absent. This gives stable item identity (a table name, not a fragile A1 range), eliminates range drift (the table tracks its own extent), and makes pre-flight a schema-vs-schema check. A spike (`spikes/google-sheets-tables/`) confirmed the API creates and reads native Tables and that the `TEXT` / `DOUBLE` / `DATE_TIME` column types round-trip verbatim; it ran under a user principal (OAuth / Apps Script), so creation under a *service-account* principal is confirmed when SA auth is wired (the README work). The tab + A1 range fallback is therefore not needed for v1. Note: the API omits `columnIndex` for column 0 on read-back (proto3 zero-omission), so read code coalesces a null `ColumnIndex` to 0.

**Writes are atomic and tab-scoped.** `Save` replaces the table's rows via a single atomic `spreadsheets.batchUpdate`, scoped to the one tab so sibling tabs are untouched; a failed write leaves no torn state, so `StorageTraits.IsTransactional = true` is honest. Replace is the default — when Flowthru owns the table it holds the full dataset every run, so replace *is* the upsert — with a `saveFunc` override for append/upsert recipes. `CanStream = false` (no cursor). Single-batch only; chunked large writes are out of v1 (they would break atomicity).

**Auth lives in DI, never in the extension.** The adapter depends on a narrow `ISheetsGateway` seam, not on `SheetsService` (concrete and unmockable). The seam speaks Flowthru-neutral tabular types (typed rows + a column schema), not Google SDK types: `Google.Apis.Sheets.v4` is confined to `SheetsServiceGateway`, which translates rows to and from the Google types (including serial-date encoding for date columns) and owns auth via an injected `SheetsService` or a `Func<SheetsService>` factory (one client per flow run via `IFlowResource`). The extension package depends only on the Google client and never sees a secret; a secret never enters the catalog or the DAG. One `SheetsService` per catalog — crossing accounts is two catalogs with two auths. Offline support lives in the main extension, not a separate companion package: a `LocalSheetsStore` (the spreadsheetId→tables map, the four ops, the serial-date read normalization, register/seed, JSON de/serialize) is the single source of truth, and a shipped `JsonFileSheetsGateway` (load-on-construct, flush-on-write, single-process) is the local-dev backend the example uses. The quota/fault-injection in-memory double — test scaffolding for the rate-limit tests — lives in the extension's test suite over the same store, so it is not shipped. (An earlier draft shipped a separate `Flowthru.Extensions.Google.Sheets.InMemory` companion package on the `Microsoft.EntityFrameworkCore.InMemory` precedent; that packaging was superseded — a file-backed gateway is a legitimate shipped backend, while the quota double is test-only.)

## Considered Options

- **A per-cell `ICellSerializable` Core marker / "cell-faithful schema" capability** — rejected. It modeled Sheets as a serialization format needing a typed-scalar marker. Native Tables make Sheets a typed tabular *store*; stores validate against their schema (the EFCore precedent) rather than carrying serialization markers, so the marker is unnecessary machinery in Core. Per-cell typing is also more than Flowthru needs — a table column has one type, like a database column.
- **`gs://` storage medium returning CSV bytes** — rejected. A Sheet is not a bytestream; CSV export collapses types and cannot express tab-scoped writes.
- **A community typed wrapper (`GoogleSheetsWrapper` et al.)** — rejected. Its job (typed rows from a sheet) is the adapter's job; it adds a single-maintainer dependency for a format supported for years.
- **A Google-SDK-typed gateway seam** — rejected. Exposing `ValueRange` / `Request` on `ISheetsGateway` would force every offline gateway (the file-backed `JsonFileSheetsGateway` and the in-memory test double) to reference `Google.Apis.Sheets.v4`. The neutral seam confines Google to a single class.
- **An Apps Script Web App backend gateway (a "no GCP project" path)** — rejected on security grounds. The seam would support it cleanly (a third `ISheetsGateway` over HTTP to a deployed Web App), but the only deployment configuration that actually avoids a GCP project — "Execute as: Me" + "Who has access: Anyone" — is a public, unauthenticated HTTPS endpoint that runs with the *deployer's full Sheets/Drive scope* (not scoped to one spreadsheet), guarded only by a roll-your-own shared token; a leaked token means read/write to every sheet the deployer owns. Every *secure* configuration ("Anyone within domain", "execute as accessing user", identity-gated) reintroduces the OAuth/GCP setup the approach was meant to avoid, and Google positions Web Apps for low-to-medium-sensitivity use, not data APIs. The service-account path is more secure by construction (per-spreadsheet sharing, no public endpoint, key rotation + audit identity), so Apps Script stays a test/spike harness only. OAuth user credentials remain a documented alternative for individuals (no public endpoint, proper per-user consent).
- **Multi-batch chunked writes** — out of v1; chunking across batches breaks atomicity (`IsTransactional` would flip to false).

## Consequences

- **A schema mismatch — including a `byte[]` column, which has no table column type — surfaces at pre-flight**, when `TRow` is validated against the table's `ColumnProperties`. This is consistent with how EFCore reports a bad entity mapping. It is one phase later than a design-time constraint would catch it, but it matches the store mental model and avoids a single-extension marker in Core.
- **The native-Tables decision is gated on a service-account spike** (`spikes/google-sheets-tables/`, tracked in the milestone). Tab + A1 range is the cell-free fallback.
- **Output size is unknowable at pre-flight** (it is produced by upstream Steps), so the single-batch ceiling (~2 MB recommended payload / 180 s timeout) is a runtime `FTGS` failure. Quota pressure (`429`, ~60 writes/min/user) is handled by retry-with-exponential-backoff at runtime, not a pre-flight count.
