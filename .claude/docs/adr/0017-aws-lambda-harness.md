# AWS Lambda support is a harness, not an orchestrator

Flowthru will support running a built Flow as an AWS Lambda via a thin **harness** — `Flowthru.Harness.AWS.Lambda` — that maps a Lambda invocation event onto a `FlowSliceStrategy` + `ExecutionOptions` and serializes the resulting `FlowResult` back as the response. A harness is the scaffolding that drives a built Flow under a given invocation mechanism; the CLI is the existing one. Harnesses live in their own source domain `src/harness/` and package family `Flowthru.Harness.*`, deliberately separate from core, Extensions, and Tools (none fit). The existing `Flowthru.Cli` is renamed `Flowthru.Harness.Cli` as the first member of that family, and the Lambda harness re-expresses the same substance as the CLI's argument parser — slice + options selection — for event payloads rather than `argv`. The managed `dotnet10` Lambda runtime (GA Jan 2026) matches Flowthru's target framework, so a built assembly runs on it directly; AWS's constructor-once / handler-per-invocation lifecycle already provides the build-once split, so the harness owns no lifecycle of its own.

Durable storage is a **separate** concern. An `s3://` `IStorageMediumProvider` (sibling to the `Http`/`EFCore` extensions, plugging into `src/core/Flowthru.Core/Data/Storage/StorageMediumResolver.cs`) has value independent of Lambda and is composed via the existing environment-swapped abstract-Catalog pattern (`examples/advanced/SpaceflightsHybridCatalog`). The harness does not own storage; it assumes a durable medium exists.

We **explicitly reject step-per-Lambda dispatch** — fanning a Flow's steps across separate Lambda invocations. That would require an `IFlowScheduler` (`src/core/Flowthru.Core/Flow/IFlowScheduler.cs`) to orchestrate cross-invocation fan-out, which contradicts Flowthru's "won't be a full piece of orchestration software" promise in `/CONTRIBUTING.md`. If that capability is ever built, it must take the form of *compiling* a Flow to an external orchestrator (e.g. AWS Step Functions) that runs the fan-out — Flowthru emits the artifact, it does not drive the fan-out itself.

## Consequences

- A "Lambda-production" catalog is a distinct storage profile admitting only network-durable media (RDS/Aurora over TCP via EFCore, `s3://` blobs). Local-disk media (file CSV/Parquet, SQLite-on-disk) and startup side-effects like `Directory.CreateDirectory` / `EnsureCreated` fail on Lambda's read-only filesystem — note `SpaceflightsHybridCatalog`'s own "Production" branch is SQLite-on-disk and is therefore *not* Lambda-compatible.
- A pre-flight guardrail should interrogate each resolved storage medium for durability in a read-only-fs host and fail at pre-flight (not runtime) when a flow binds a non-durable medium, turning the default deployment mistake into a fail-fast diagnostic.
